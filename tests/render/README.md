- python3 tests/startup/run.py and sh tests/audio/run.sh: unchanged allocation/task/startup and SFX/music regression coverage, normal and ASan/UBSan.

## Root causes

**Melt:** the old drawTask wipe branch mapped source world rows 0..207 to all 240 physical rows. Ordinary gameplay mapped those same rows to 198 physical rows, then added 10 ammo + 32 status rows. Thus the final wipe was 240/198 = 1.2121 times the ordinary world height, followed by a visible snap. A raw engine wipe also lacked the custom physical HUD composition. Applying a static HUD afterwards would float art over columns that had not melted yet.

DoomPresentation is now the single retained world/UI/ammo/status mapping. Both indexed wipe endpoints are composed *before* the original engine melt, into its existing allocations at physical pitch/height. drawTask sends the resulting physical wipe without reinterpreting its rows. All HUD source pixels and decorative backing pixels participate in the melt; volume feedback remains strictly after scene composition in the LCD scanline. The frame wipe flag also covers transitions out of gameplay. Native menu art is already part of each endpoint, so native-coordinate menu redraws are skipped only inside physical wipes. Consecutive wipes retain already-physical start pixels without double mapping. The next native draw forces HUD and border refresh because the engine framebuffer held physical pixels at the end of the wipe.

**Sky:** SCREENHEIGHT is 240, full world height is 208, centery is 104 and viewport y is zero. The old sky used the horizontal psprite inverse scale 320/280 with unchanged skytexturemid = 100 texels. Its top sample was 100 - 104 * (320/280) = -18.857 texels; the shared wall drawer's &127 wrapped that to row 109 of a 128-row texture. It crossed the texture's real top around source y=17 (about 17 physical pixels). This mathematically reproduces the reported different strip above the outdoor sky; it is not a 20-pixel display offset, and interiors did not use that sky branch.

R_SkyScale restores the original 168-row sky angular span over the 208-row world: full-size step 168/208 and top sample 16, exactly the original 100 - 84. Only sky sampling changes; world/weapon projection, viewwindow placement, menu scaling and WAD files remain unchanged. A dedicated sky column drawer wraps against textureheight rather than a wall-specific hardcoded mask. Wrapping is normalized once per column and maintained without per-pixel division. The existing local DOOM.WAD was inspected read-only: SKY1..4 textures and patches are 256x128, each patch column has a single 128-pixel post. No WAD data was copied into the repository. This confirms the actual standard assets fit the sampler; arbitrary custom-WAD patch-loader behavior is not newly guaranteed.

## Cost and verification limits

No new framebuffer or persistent heap allocation. The shared geometry object is 1636 bytes on the host (the old coordinate maps were already 1600 bytes); the draw owner initializes it once, and the game task briefly constructs one for each endpoint. Two extra physical compositions occur only per transition. Existing melt endpoint allocations remain 320x240 bytes each; physical 280x240 melt transform scratch falls from 76800 to 67200 bytes and its column-position array from 1280 to 1120 bytes. Every LCD pixel is still sent once per frame, with one address window. Sky has a 64-bit scale division per sky plane and two normalization remainders per nonempty column, then a bounded add/compare/subtract pixel loop. ESP32 execution time, stack headroom, RAM/flash artifact sizes and device presentation remain unmeasured.

The supported panel rotations fit within the existing 320x240 allocation and have even width. Normal native RGB letterboxes are black; indexed wipe letterboxes use Doom palette index zero (black in the standard supported palettes). No firmware build, PlatformIO operation, dependency install/download, package, flash, screenshot, device verification, merge or push was performed. A device comparison is still required before claiming the owner's exact outdoor symptom is resolved. If it persists, capture the same outdoor viewpoint before/during/after entry and identify WAD/map/view-size/rotation; the source seam above is independently proven and removed by the synthetic production renderer tests.
